# PROJECT RULES — «Погода» (Android, Jetpack Compose) по референс-видео

## СУТЬ
Погодное приложение из refs/ (кадры моего видео). карточки, премиум, реклама,
облака-пальцем, модалка про траву). 

## ГРАНИЦЫ
Пишу только в этом воркспейсе. refs/ и refs_src/ не модифицировать (только читать/резать в refs/).

## ИСТОЧНИКИ ПРАВДЫ
1) refs/*.png — UI: состав экранов, порядок карточек, подписи RU, цвета (голубая и тема, которая выпадает с рулетки).
2) open-meteo.com — данные: current/hourly/daily, geocoding, WMO-коды погоды.
   ДОКУМЕНТАЦИЮ ЧИТАТЬ ЧЕРЕЗ ВЕБ-ПОИСК перед написанием клиента. API-ключей нет и не надо.
3) Jetpack Compose / Material3 docs — через веб-поиск, не по памяти.
4) ACCEPTANCE.md — матрица требований и критериев приёмки; ведёт `judge`.

## ТЕХ
Kotlin + Compose + Material3, minSdk 24, Gradle Kotlin DSL, kotlinx.serialization.
Кэш последней погоды (DataStore) + баннер «нет сети». Гео по умолчанию Санкт-Петербург, потом Москва, поиск городов.

## РОЛИ И СУБАГЕНТЫ (через `subagent`/`subagent_fork`, модель deepseek-v4.1-flash)
Главный агент — Оркестратор проекта. Он координирует задачи, распределяет работу и сводит отчёты. Сам код не пишет, APK не собирает, adb не дёргает.

### 1. Написание кода (Кодеры)
- `ui-coder` — верстка Jetpack Compose по refs/*.png: карточки, шрифты, темы Material3, анимации («облака пальцем», рулетка тем), модалки. Держит контракт UI state с `data-coder`, бизнес-логику в composables не пишет.
- `data-coder` — сетевой слой Open-Meteo, кэш DataStore, оффлайн-детекция, города, репозитории, модели, ViewModels. Пишет unit-тесты на новую логику; выдуманные данные не отдаёт — при отсутствии данных пишет «нет данных».

### 2. Сборка и устройство
- `device-qa` — финальный `assembleDebug`, установка на Sony G8342, `shots/`, `gfxinfo`, `logcat`, запись экрана для динамики. Код не правит. Кодеры могут сами запускать `compileDebugKotlin` и `testDebugUnitTest`; сборка и установка APK — только через `device-qa`. `feature-qa` тестирует уже установленное приложение (input/swipe), но APK не переустанавливает.

### 3. Тестирование и критика (отдельные роли, не заменяют друг друга)
- `feature-qa` — сценарии: Open-Meteo, кэш, оффлайн, города, экраны «Карта/Список/Поиск/Вид», модалки, deep links в Яндекс Go/Еду, доступность внешних источников из РФ без VPN (OSM, Wikimedia/Coil), logcat. Проверяет по матрице требований `ACCEPTANCE.md`.
- `visual-critic` — единый визуальный аудитор (статика + динамика): сверка `shots/` с `refs/*.png` и `refs_src/reference.mp4`, порядок блоков, типографика, тексты RU, темы, облака, рулетка, шторки. Для экранов без референсов — по критериям `ACCEPTANCE.md`. Вердикт PASS/FAIL. Код не правит.
- `code-reviewer` — критик кода: дифф, архитектура, Compose state/рекомпозиции, корутины, обработка ошибок, тесты, отсутствие заглушек. Прогоняет `testDebugUnitTest`. Вердикт PASS/FAIL. Код не правит.
- `perf-qa` — производительность: p50/p95 кадра, jank, `gfxinfo framestats`, baseline profile, release-подобный buildType, 60 FPS на G8342. Обязателен для релизных фаз и при просадке FPS. Код не правит.

### 4. Финальный судья и гейткипер (Внутренняя приемка)
- `judge` — независимый финальный гейт. Не дублирует `visual-critic` и `code-reviewer`: проверяет матрицу `ACCEPTANCE.md`, свежесть доказательств, наличие PASS от `feature-qa` + `visual-critic` + `code-reviewer` (+ `perf-qa` для релиза), делает spot-check 2–3 экранов и выносит PASS/REJECT. Пока нет PASS — результат пользователю не отдаётся.

### 5. Модель и эффорт (экономия)
- Базовая модель — `deepseek-v4.1-flash`; дефолт профиля — `reasoningEffort: high`.
- `max` — **только** `judge` и `code-reviewer`: финальный вердикт и поиск тонких дефектов
  (гонки, отмена, обработка ошибок) реально выигрывают от максимального эффорта.
- `high` — `ui-coder`, `data-coder`, `visual-critic`, `feature-qa`, `perf-qa`.
- `low` — `device-qa` (механические adb-шаги, сборка, установка, скриншоты) и мелкие
  точечные правки в любой роли.
- `visual-critic`, `judge`, `feature-qa`, `device-qa`, `ui-coder` не переводятся на text-only
  модели: им нужны изображения (`refs/*.png`, `shots/*.png`).
- Дешёвые text-only модели (`iceman-contributor-free`, `glm-5.3-flash`) — только для
  `data-coder` и мелких правок, после проверки на реальных задачах; не по умолчанию.
- Оркестратор передаёт `reasoning_effort` явно при каждом запуске субагента.

## ЦИКЛ СДАЧИ (QUALITY GATE):
```
[ui-coder / data-coder] (compile + unit tests)
         ↓
    [device-qa] (финальная сборка + install на G8342 + shots/ + gfxinfo/logcat)
         ↓
[feature-qa] [visual-critic] [code-reviewer] [perf-qa*]
         ↓
      [judge] (матрица ACCEPTANCE.md + свежесть доказательств + spot-check)
      ├── FAIL: возврат конкретным ролям с перечнем правок (цикл повторяется)
      └── PASS (100% идеально): только теперь финальный отчет отдается ПОЛЬЗОВАТЕЛЮ
```
`*` `perf-qa` — для релизных фаз и при просадке FPS.

### ПРАВИЛА ПРИЕМКИ ФАЗЫ:
1. Главному оркестратору ЗАПРЕЩЕНО собирать APK и дергать adb. Сборка, установка и скриншоты — только через `device-qa`; `feature-qa` может использовать adb для тестовых действий с уже установленным приложением.
2. Главному оркестратору ЗАПРЕЩЕНО отдавать результат пользователю в обход `judge`.
3. Конец фазы = вердикт PASS от `judge`, подтвержденный скриншотами `shots/`, логами сборки и отсутствием багов.
4. `visual-critic` и `code-reviewer` — отдельные обязательные проверки. `judge` не подменяет их и не отменяет.
5. PASS от `judge` возможен только при PASS от `feature-qa`, `visual-critic`, `code-reviewer` (+ `perf-qa` для релиза) и отсутствии «не проверено» по требованиям фазы в `ACCEPTANCE.md`.
6. Отчёт каждой роли — файл в `_history/reports/phase-N/<role>.md`; оркестратор сохраняет отчёт, `judge` читает файлы, а не пересказы в чате.
7. Если телефон/сеть недоступны — статус BLOCKED и честный отчёт, а не выдуманные скриншоты/замеры.
